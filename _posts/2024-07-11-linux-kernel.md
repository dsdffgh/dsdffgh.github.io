### 进程

#### CFS调度的调度策略有哪几种

CFS（Completely Fair Scheduler）是Linux内核中用于进程调度的一种调度策略，其主要目标是提供公平性和高度预测性的进程调度。CFS 主要有以下几种调度策略和特性：

1. **红黑树调度策略**：
    - CFS 使用红黑树作为进程的运行队列，每个进程节点都有一个虚拟运行时间（virtual runtime），代表进程已经占用的 CPU 时间。
    - 红黑树是一种自平衡二叉查找树，可以快速进行插入、删除和查找操作，保证了 CFS 调度的高效性。
2. **公平性调度**：
    - CFS 的核心思想是保证所有进程在同样的时间段内获得相同的 CPU 时间片，即实现“完全公平”（completely fair）的调度。
    - 每个进程的虚拟运行时间（virtual runtime）根据进程在运行队列中所占据的权重动态调整，以实现公平分配 CPU 资源。
3. **预测性调度**：
    - CFS 设计上允许进程的 CPU 使用时间可预测，即使在负载高的情况下，也能保持相对稳定的响应时间。
    - 虚拟运行时间的动态调整使得 CFS 能够在不同的负载情况下进行自适应，确保高优先级进程可以更快地得到响应，而低优先级进程也能得到公平的调度。
4. **实时任务支持**：
    - CFS 提供对实时任务的支持，通过控制任务的优先级和调度策略，可以在不破坏公平性的前提下，保证实时任务的响应性和及时性。
5. **Nice 值调整**：
    - Nice 值是用来调整进程的静态优先级（static priority），通过调整 Nice 值，可以间接影响进程在 CFS 调度中的虚拟运行时间，从而影响 CPU 时间片的分配。

总结来说，CFS 是一种基于红黑树的公平且具有预测性的调度策略，其设计目标是在多任务环境下，尽可能地公平地分配 CPU 资源，并确保系统中的不同类型的任务（包括实时任务和普通任务）都能得到合理的调度。

#### 普通进程与内核线程有如下区别：

- 内核线程只运行在内核态，而普通进程既可以运行在内核态，也可以运行在用户态；
- 内核线程只使用 3-4GB (假设为 32 位系统) 的内核地址空间（共享的），但普通进程由于既可以运行在用户态，又可以运行在内核态，因此可以使用 4GB 的虚拟地址空间

#### [**父进程、子进程的关系以及区别**](https://www.cnblogs.com/swk0918/p/14444919.html)

父进程和子进程的关系

1. **创建**: 父进程通过调用 `fork()` 系统调用创建一个子进程。调用 `fork()` 后，系统会创建一个新的进程，称为子进程，父进程继续执行原来的代码。
2. **继承**: 子进程继承父进程的大部分资源和环境变量，如文件描述符、信号处理方式、用户和组 ID 等。
3. **独立性**: 尽管子进程继承了父进程的资源和环境变量，但它是一个独立的进程，有自己唯一的进程 ID（PID）。

区别：

- fork的返回值
- 进程ID
- 不同的父进程ID
- 子进程的tms_utime、tms_stime、tms_sutime、tms_ustime设置为0
- 父进程设置的锁，子进程不继承
- 子进程的未决告警被清除
- 子进程的未决信号集设置为空集

#### 线程共享和独占的资源

线程共享的资源包括虚拟地址空间（代码区堆区栈区数据区）、文件描述符、信号处理、进程资源限制、环境变量、C 库（动态链接库）、调度策略等，而线程私有的资源是上下文，包括线程 ID、栈、寄存器状态、线程局部存储等。

#### 虚拟内存分布

在Linux系统中，虚拟内存的地址空间通常分为多个区域，不同区域负责不同类型的数据和任务。一般来说，虚拟内存空间分为以下几大部分：

#### 1. 用户空间（User Space）

用户空间是进程在用户态运行时所使用的地址空间，通常从较低地址开始。Linux中的用户空间地址分布如下：

- **代码段（Text Segment）**：存储可执行代码的区域，通常是只读的，以防止程序意外修改代码。
- **数据段（Data Segment）**：存放已初始化的全局变量和静态变量。
- **BSS段（Block Started by Symbol Segment）**：用于未初始化的全局变量和静态变量。在程序加载时，这些变量会被初始化为0。
- **堆（Heap Segment）**：用于动态分配内存，堆的大小可以在程序运行时通过系统调用 `malloc`、`free` 等进行调整。堆空间向高地址扩展。
- **栈（Stack Segment）**：用于存储局部变量和函数调用的返回地址等信息。栈从高地址向低地址扩展。

#### 2. 内核空间（Kernel Space）

内核空间专门为内核运行而分配，并且用户进程不能直接访问。一般来说，内核空间位于地址空间的较高地址，包含以下内容：

- **内核代码**：用于内核本身的可执行代码。
- **内核数据**：存储内核使用的全局变量和静态变量。
- **设备内存映射**：为与硬件设备交互，通常会为设备分配专门的地址区域。
- **内核堆**：用于内核分配动态内存。
- **内核栈**：每个进程都有一个单独的内核栈，用于内核态运行时的函数调用和局部变量。

#### 3. 共享内存和动态链接库

共享内存和动态链接库通常映射在用户空间的中间地址附近，常见内容包括：

- **共享内存段**：通过`shmget`等系统调用创建，允许多个进程共享同一块内存。
- **动态链接库**：动态加载的共享库，如`.so`文件，通常通过`mmap`加载到内存中供进程调用。

#### 4. 内存映射文件区（Memory Mapped Files）

通过`mmap`系统调用，可以将文件映射到内存中，以便进程可以像访问内存一样访问文件内容。内存映射文件区位置通常动态调整，以避免与堆和栈冲突。

#### 5. 保留区域（Reserved Area）

为了防止堆、栈或内核区域之间的冲突，一些特定的地址空间会被保留，不会被直接分配给进程使用。这些区域可以根据需要进行特殊映射或用于调试和保护目的。

#### 虚拟内存布局示例

对于一个典型的32位Linux进程，虚拟内存布局可能如下：

```
0x00000000          - 0x08000000 : 未使用区域
0x08048000          - 0x08049000 : 代码段 (Text)
0x08049000          - 0x0804A000 : 数据段 (Data)
0x0804A000          - 0x0804B000 : BSS段
0x0804B000          - 0xBFFFFFFF : 堆区 (Heap)
0xC0000000          - 0xEFFFFFFF : 保留区 (Reserved)
0xF0000000          - 0xFFFFFFFF : 栈区 (Stack)
0xF7F00000          - 0xF7FFFFFF : 动态链接库 (Shared Libraries)
0xFFF00000          - 0xFFFFFFFF : 内核空间 (Kernel Space)

```

对于64位系统，地址空间更大，布局更灵活，但基本结构相似。

### 内核和用户空间

#### **linux中内核空间及用户空间的区别？**

| **特点** | **内核空间（Kernel Space）** | **用户空间（User Space）** |
| --- | --- | --- |
| 定义 | 操作系统内核运行的内存区域 | 用户应用程序运行的内存区域 |
| **访问权限** | 只有内核代码可以访问，普通用户进程不能直接访问 | 用户进程运行在受限模式下，只能访问用户空间内存 |
| **内存布局** | 位于系统虚拟内存地址的高端，固定大小 | 位于系统虚拟内存地址的低端，动态调整 |
| **安全性** | 运行在最高权限级别，错误影响整个系统 | 运行在受限权限级别，错误只影响当前进程 |
| **访问方式** | 系统调用和内核 API | 标准库和用户态 API |
| **性能** | 高效率，直接操作硬件 | 受限效率，通过系统调用与内核交互 |

#### **用户空间与内核通信方式有哪些？**

在 Linux 系统中，用户空间和内核空间之间的通信是一个关键问题。由于两者运行在不同的权限级别，并且用户空间的进程不能直接访问内核空间，因此需要通过各种机制实现它们之间的通信。以下是常见的用户空间和内核空间的通信方式：

#### 1. 系统调用（System Calls）

系统调用是用户空间与内核空间通信的最基础方式。用户进程通过系统调用请求内核执行特定的服务（如文件操作、进程控制、网络通信等）。

- **例子**: `open()`, `read()`, `write()`, `ioctl()` 等。

#### 2. `/proc` 和 `/sys` 文件系统

这两个伪文件系统提供了一种查看和修改内核状态的接口。

- **/proc 文件系统**: 提供进程和系统信息。用户可以读取这些文件获取内核状态信息。
    - **例子**: `/proc/cpuinfo`, `/proc/meminfo`
- **/sys 文件系统**: 提供对设备和内核子系统的配置接口。
    - **例子**: `/sys/class/net/eth0/address` (查看网络接口的 MAC 地址)

#### 3. 设备文件（Device Files）

设备文件通常位于 `/dev` 目录下，用户进程可以通过标准的文件操作系统调用（如 `open`、`read`、`write`）与设备驱动程序通信。

- **字符设备**: 如串口设备，使用 `cdev` 接口。
- **块设备**: 如硬盘设备，使用 `blockdev` 接口。

#### 4. Netlink 套接字

[linux_kernel_wiki/文章/Linux用户空间与内核空间通信(Netlink通信机制).md at main · 0voice/linux_kernel_wiki](https://github.com/0voice/linux_kernel_wiki/blob/main/文章/Linux用户空间与内核空间通信(Netlink通信机制).md)

Netlink 是一种进程间通信机制，专门用于在用户空间进程和内核之间传递数据。常用于网络子系统和内核模块之间的通信。

- **例子**: 使用 `netlink` 套接字配置网络接口、路由表等。

#### 5. ioctls

`ioctl` 是一种设备控制接口，允许用户进程发送命令到设备驱动程序或内核模块。`ioctl` 提供了比标准系统调用更多的灵活性。

- **例子**: 网络接口配置（`SIOCGIFADDR` 获取 IP 地址）。

#### 6. 内存映射（mmap）

`mmap` 系统调用允许用户进程将文件或设备内存映射到进程的地址空间，从而实现高效的内存共享。

- **例子**: 映射设备内存或共享内存段，进行高效的用户态与内核态数据传递。

#### 7. 中断和信号

信号是一种异步通知机制，内核可以通过信号向用户空间进程发送事件通知。用户进程可以设置信号处理函数来处理这些信号。

- **例子**: `SIGINT`、`SIGKILL`、`SIGUSR1`

#### 8. 消息队列、信号量和共享内存（System V IPC）

System V 提供了一套进程间通信机制，包含消息队列、信号量和共享内存，用户进程可以通过这些机制与内核模块进行通信。

- **消息队列**: 使用 `msgget`, `msgsnd`, `msgrcv` 进行消息传递。
- **信号量**: 使用 `semget`, `semop`, `semctl` 控制并发。
- **共享内存**: 使用 `shmget`, `shmat`, `shmdt`, `shmctl` 共享数据。

#### 9. Futex（Fast Userspace Mutex）

`futex` 是一种快速用户空间互斥锁机制，允许用户进程在用户空间进行锁操作，只有在争用的情况下才进入内核，减少了系统调用的开销。

- **例子**: `futex()` 系统调用，用于实现高效的用户态互斥锁。

#### 10. 调试接口

调试器（如 `gdb`）和内核调试接口（如 `kprobes`, `tracepoints`）允许用户进程和内核模块进行调试和分析。

- **例子**: `ptrace` 系统调用，用于进程调试。

#### 11. eBPF（Extended Berkeley Packet Filter）

eBPF 提供了一种在内核中运行用户定义代码的机制，允许用户空间程序注入自定义逻辑到内核，进行监控和网络数据处理等任务。

- **例子**: 使用 `bpf()` 系统调用加载和管理 eBPF 程序。

通过这些通信方式，用户空间和内核空间可以高效、安全地交互，确保系统的稳定性和安全性，同时提供丰富的功能和灵活性。

在这几个通信方式中，选择netlink，原因如下：

```
全双工：procfs是基于文件系统，用于内核向用户发送消息；syscall是用户访问内核。它们都是单工通信方式。netlink是一种特殊的通信方式，用于在内核空间和用户空间传递消息，是一种双工通信方式。使用地址协议簇AF_NETLINK，使用头文件include/linux/netlink.h；
易于添加：为新特性添加system call、或者procfs是一件复杂的工作，它们会污染kernel（内核），破坏系统的稳定性，这是非常危险的。Netlink的添加，对内核的影响仅在于向netlink.h中添加一个固定的协议类型，然后内核模块和应用层的通信使用一套标准的API。

```

#### linux的内核子系统包括哪些

Linux内核主要由5个子系统组成：进程调度（SCHED），内存管理（MM），虚拟文件系统（VFS），网络接口（NET），进程间通信（IPC）。

#### **kmalloc和vmalloc的区别**

1，vmalloc分配的一般为高端内存，只有当内存不够的时候才分配低端内存；kmallco从低端内存分配。

2，vmalloc分配的物理地址一般不连续，而kmalloc分配的地址连续，两者分配的虚拟地址都是连续的；

3，vmalloc分配的一般为大块内存，而kmaooc一般分配的为小块内存，（一般不超过128k);

#### **内核程序中申请内存使用什么函数？**

**答案：**kmalloc()、kzalloc()、vmalloc()。

**解读：**

（1）void *kmalloc(size_t size, gfp_t flags);

①申请连续的物理内存，这对于要进行DMA的设备十分重要，但大小不能超过128KB，其中有16B是被页描述符占用了。

②较常用的flag有GFP_ATOMIC（分配内存的过程是一个原子过程）、GFP_KERNEL（正常分配内存）、GFP_DMA（给DMA控制器分配内存）。

③对应的内存释放函数为void kfree(const void *objp)。

（2）void *kzalloc(size_t size, gfp_t flags);

①kzalloc()相对kmalloc()只是额外增加了__GFP_ZERO标志，除了申请内存外，还会对申请到的内存内容清零。

②对应的释放函数也是kfree()。

（3）void *vmalloc(unsigned long size);

①申请虚拟地址连续的内存空间，但其对应的物理内存不一定连续，因此对申请的内存大小没有限制。

②对应的内存释放函数为void free(const void *addr)。

③注意：vmalloc()和vfree()可以睡眠，因此不能在中断上下文调用。

### linux中不需要设备树也可以自动探查到当前已连接的设备，这个机制是怎么实现的

在 Linux 中，即使不使用设备树（Device Tree），内核仍然可以自动探查并识别当前已连接的设备。实现这种机制的关键在于现代计算机和总线系统的**自我描述**功能和**即插即用（Plug and Play, PnP**）技术。以下是主要的机制和协议：

#### 1. **PCI 总线（Peripheral Component Interconnect）**

- **PCI**（包括 PCIe，PCI Express）是现代计算机中最常见的硬件总线之一，几乎所有的硬件设备（显卡、网卡、声卡等）都通过 PCI 总线连接到系统。
- **即插即用机制**：PCI 设备通过总线和设备的协作，实现自我描述。每个 PCI 设备有一个**配置空间**，它包含有关设备类型、厂商 ID、设备 ID 和资源需求（如内存地址范围、中断号）的信息。
    - Linux 内核在系统启动时会遍历所有的 PCI 总线，读取这些设备的配置空间信息，然后加载相应的驱动程序。
    - 这种机制不依赖于设备树，因为设备能够自我描述，内核可以通过 PCI 的标准机制自动探测设备并初始化它们。
- **设备扫描**：通过读取总线上的每个设备，内核能探测并识别当前已连接的所有 PCI 设备。

#### 2. **USB（Universal Serial Bus）总线**

- **USB** 是另一种自我描述的总线类型，广泛用于连接外围设备（如键盘、鼠标、存储设备等）。
- **USB 设备描述符**：每个 USB 设备通过设备描述符告诉主机其类型、厂商 ID、产品 ID 和支持的功能。主机在检测到 USB 设备连接时，会读取这些描述符，并根据设备类型加载相应的驱动程序。
- Linux 内核可以通过 USB 协议的标准发现机制，自动识别和加载设备驱动，无需手动干预或使用设备树。

#### 3. **ACPI（Advanced Configuration and Power Interface）**

- **ACPI** 是一种标准，用于管理电源配置和设备探测，主要应用于 x86 体系结构的 PC 和服务器。
- **设备描述表（DSDT 和 SSDT）**：ACPI 提供了一种通过 ACPI BIOS（基本输入输出系统）提供的设备描述表来枚举和配置设备的方法。系统启动时，内核通过读取 ACPI 提供的表，可以获取与设备相关的信息。
- 设备表中的信息通常包括电源状态、设备资源配置、系统中断等。通过 ACPI，Linux 能够识别各种设备并加载相应的驱动程序，而不依赖设备树。

**查看 ACPI 表**：

- 可以通过 `dmesg | grep ACPI` 来查看 ACPI 相关的启动信息。

#### 4. **固件接口**

- **BIOS/UEFI**：现代的计算机系统采用 UEFI 代替传统的 BIOS，它为操作系统提供了设备和资源的基本信息。在系统启动时，BIOS/UEFI 会对设备进行初始化，并为操作系统提供设备的基本信息和配置选项。
- **操作系统发现设备**：BIOS/UEFI 通过不同的表格或接口（如 SMBIOS 或 ACPI）向操作系统提供设备信息。操作系统可以基于这些信息加载合适的驱动，并正确初始化设备。

#### 5. **热插拔机制**

- *热插拔（Hotplugging）**是指在系统运行过程中，设备可以被插入或移除，系统能够自动识别设备的变化并做出相应的处理。Linux 内核中集成了对热插拔设备的支持，尤其是在 USB 和 PCI 设备上。
- 当设备插入时，系统会触发热插拔事件，通知内核去探测新设备，并加载相应的驱动程序。

#### 6. **内核模块自动加载**

- Linux 内核通过 **udev** 等用户空间工具，可以自动检测到新设备的连接并动态加载相应的内核模块（驱动程序）。

- 当设备被探测到时，内核会通过设备 ID、厂商 ID 等信息，查找相应的驱动程序并自动加载，无需用户干预。

### **malloc 和缺页中断（Page Fault）的关系**

#### **1. `malloc` 的作用**

- `malloc(size_t size)` 用于 **在堆上分配内存**，但它的行为比表面上看起来的更复杂：
    - 它**不会立即从操作系统获取物理内存**，而是向 **运行时库**（如 `glibc` 的 `malloc`）申请内存。
    - 运行时库使用 `brk/sbrk` 或 `mmap` 来向内核请求虚拟地址空间。
    - 申请的虚拟地址最初可能**不会映射到物理内存**，直到进程实际访问该内存时，才会触发**缺页中断（Page Fault）**，让操作系统分配物理页。

---

#### **2. `malloc` 过程中的内存分配**

**（1）用户调用 `malloc`**

- `malloc` 可能会从已管理的空闲内存块（Free List）中分配，如果没有合适的块：
    - 小块（通常 < 128 KB）：使用 `sbrk` 增长堆（Heap）。
    - 大块（通常 ≥ 128 KB）：使用 `mmap` 申请新的虚拟地址空间。

**（2）虚拟地址分配**

- 通过 `sbrk` 或 `mmap` 分配的内存只是**虚拟地址空间**，操作系统尚未分配**物理内存页**。

**（3）程序第一次访问 `malloc` 分配的内存**

- 由于 `malloc` 返回的内存区域可能**尚未映射到物理页**，访问该区域（如 `p = 0;`）时，会触发 **缺页中断（Page Fault）**。

---

#### **3. 缺页中断（Page Fault）**

**（1）发生条件**

- 进程访问**尚未映射到物理内存**的虚拟地址时，CPU 触发**缺页异常**（Page Fault）。
- 操作系统检查该地址是否属于进程的合法地址空间：
    - **是合法地址**（如 `malloc` 分配的地址）：分配物理页，并更新页表。
    - **非法地址**（如访问 `NULL`）：触发 `Segmentation Fault`（段错误）。

**（2）处理过程**

1. **CPU 检测到缺页异常** → 触发 **缺页中断**（Page Fault）。
2. **操作系统（MMU）检查页表**：
    - 若是合法的 `malloc` 分配区域，分配物理页。
    - 若是非法访问，向进程发送 `SIGSEGV`。
3. **内核从空闲内存池分配物理页**（可能涉及页面换入/换出）。
4. **更新页表**，映射虚拟地址到物理地址。
5. **恢复进程执行**，程序继续访问该内存。

---

#### **4. 示例：观察 `malloc` 触发 Page Fault**

```c
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <unistd.h>
#include <sys/time.h>
#include <sys/resource.h>

int main() {
    size_t size = 1024 * 1024 * 100; // 100 MB
    char *p = (char *)malloc(size);  // 仅分配虚拟地址空间
    printf("Memory allocated, but not accessed.\n");

    getchar(); // 暂停，检查进程的虚拟内存大小

    memset(p, 0, size); // 触发 Page Fault，分配物理页
    printf("Memory initialized (Page Fault occurs).\n");

    getchar(); // 再次暂停，观察物理内存占用情况

    free(p);
    return 0;
}

```

**分析：**

1. `malloc(size)` 只是**申请虚拟地址**，不会立即分配物理页。
2. `getchar()` 让程序暂停，此时可以用 `pmap <pid>` 观察虚拟内存。
3. `memset(p, 0, size)` 访问该内存，触发 Page Fault，导致物理内存分配。
4. `getchar()` 让程序再次暂停，此时 `pmap <pid>` 显示物理内存增加。

---

#### **5. 关键结论**

- `malloc` 只是申请**虚拟地址空间**，物理页的分配由 **缺页中断（Page Fault）** 触发。
- `mmap` 分配的大块内存通常不会立即分配物理页，除非 `MAP_POPULATE` 选项被使用。
- 频繁触发 Page Fault 可能会**影响性能**，导致进程被阻塞，影响实时性应用。

#### **优化建议**

1. **避免频繁 Page Fault**：
    - 预热内存：`memset(p, 0, size)` 提前触发缺页，避免后续使用时频繁中断。
    - `mlock()` 锁定内存，避免换出，提高实时性（适用于高性能应用）。
2. **减少碎片化**：
    - 使用 `mmap` 直接分配大块内存，减少 `sbrk` 的碎片问题。
3. **使用 `MAP_POPULATE` 预加载页**（适用于 `mmap`）：
    
    ```c
    mmap(NULL, size, PROT_READ | PROT_WRITE, MAP_PRIVATE | MAP_ANONYMOUS | MAP_POPULATE, -1, 0);
    ```
    
    这样可以**提前分配物理页**，避免后续访问时触发 Page Fault。
    

---

#### **总结**

| **概念** | **malloc** | **缺页中断（Page Fault）** |
| --- | --- | --- |
| **作用** | 申请虚拟地址空间 | 将虚拟地址映射到物理页 |
| **是否分配物理内存** | 否，初始时只分配虚拟地址 | 是，访问该地址时触发 Page Fault 进行分配 |
| **触发条件** | 调用 `malloc(size)` | 访问 `malloc` 分配的未映射页面 |
| **处理方式** | 运行时库调用 `sbrk` 或 `mmap` | OS 分配物理页，更新页表 |
| **优化方法** | 预热 `memset`，使用 `mmap` | `MAP_POPULATE`，`mlock()` |

**结论**：

- `malloc` 本身不会分配物理内存，访问未映射页面时，触发 **缺页中断（Page Fault）**，由操作系统完成物理页分配。
- `Page Fault` 是 `malloc` 内存延迟分配的核心机制，适当优化可以提升程序性能。

### **linux中RCU原理？**

read-copy-update，是对rw-lock的优化。因为锁机制存在两问题：

1. 锁机制会破坏流水线效率，而且rw锁中写锁有排他性，无法并发读写。降低性能
2. CPU数量越多，锁机制实现的同步访问效率越低。导致一致性访问的扩展性差。

RCU的思路实际上很简单，如下所示：

1. 对于读操作，可以直接对共享资源进行访问，但是前提是需要CPU支持访存操作的原子化，现代CPU对这一点都做了保证。但是RCU的读操作上下文是不可抢占的（这一点在下面解释），所以读访问共享资源时可以采用read_rcu_lock()，该函数的工作是停止抢占。

2 . 对于写操作，其需要将原来的老数据作一次备份（copy），然后对备份数据进行修改，修改完毕之后再用新数据更新老数据，更新老数据时采用了rcu_assign_pointer（）宏，在该函数中首先屏障一下memory，然后修改老数据。这个操作完成之后，需要进行老数据资源的回收。操作线程向系统注册回收方法，等待回收。采用数据备份的方法可以实现读者与写者之间的并发操作，但是不能解决多个写者之间的同步，所以当存在多个写者时，需要通过锁机制对其进行互斥，也就是在同一时刻只能存在一个写者。

3. 在RCU机制中存在一个垃圾回收的daemon，当共享资源被update之后，可以采用该daemon实现老数据资源的回收。回收时间点就是在update之前的所有的读者全部退出。由此可见写者在update之后是需要睡眠等待的，需要等待读者完成操作，如果在这个时刻读者被抢占或者睡眠，那么很可能会导致系统死锁。因为此时写者在等待读者，读者被抢占或者睡眠，如果正在运行的线程需要访问读者和写者已经占用的资源，那么死锁的条件就很有可能形成了。

### mmap实现原理，机制

把文件映射到进程地址空间，应用可以像操作内存一样访问数据，适合需要随机读取、局部修改、按需解析文件内容的场景。需要频繁随机访问文件内容，比如数据库页缓存、消息队列消费、索引文件读取。

**先说一下mmap的原理：在进程的虚拟内存开辟一块空间，映射到内核的物理内存，并建立和文件的关联**，再把文件内容读到这块内存；后续直接读写这块建立好映射的内存！等到进程退出或出意外奔溃，操作系统把映射内存的数据重新写回磁盘的文件！
do_mmap 代码有很多，但是核心功能其实并不复杂：找到空闲的虚拟内存地址，并根据不同的文件打开方式设置不同的vm标志位flag！在函数末尾处调用了mmap_region函数，核心功能是创建和初始化虚拟内存区域，并加入红黑树节点进行管理。

### mmap比fread读的快的原因。

[blog.51cto.com](https://blog.51cto.com/liangchaoxi/4051948)

用fread/fwrite方式访问硬盘，用户须向内核指定要读多少，内核再把得到的内容从内核缓冲池拷向用户空间；写也须要有一个大致如此的过程。这样在访问IO的时候就多经历了这么一个内核的buffer，造成速度的限制。`mmap` 可以减少系统调用的次数和数据复制的开销，并且它利用了内存映射的高效访问模式和操作系统的缓存机制。

#### 1. 系统调用的开销

- **`mmap`**：映射文件到内存只需进行一次系统调用。之后，数据的访问和操作都是直接在内存中完成的，这可以减少频繁的上下文切换和系统调用开销。
- **`fread`**：每次读取操作通常需要执行多个系统调用（例如，`read`），这会引入上下文切换的开销。文件数据需要从内核空间复制到用户空间，这也是性能开销的一部分。

#### 2. 缓存和页面置换

- **`mmap`**：文件的映射在内存中创建了虚拟地址空间，操作系统会自动处理页面置换和缓存。这意味着读取的数据可能已经被操作系统缓存，从而提高访问速度。
- **`fread`**：`fread` 使用的缓冲区可能并不会充分利用操作系统的页面缓存。如果 `fread` 请求的数据大小超过缓冲区大小，则可能导致频繁的 I/O 操作和缓存管理开销。

#### 3. 数据访问模式

- **`mmap`**：通过内存映射，文件数据可以被映射到内存中，以支持随机访问。这种方法适合大文件和需要随机读取的应用场景，因为它可以减少重复的文件访问。文件的整个内容可以在内存中映射，而不需要将其全部加载到内存中。操作系统只加载实际访问的页面，这有助于处理大文件并节省内存。
- **`fread`**：`fread` 通常按块读取文件数据，可能需要多次读取操作才能满足需求，特别是当访问模式涉及随机访问时，性能可能会受到影响。并且大文件处理时可能需要频繁的 I/O 操作。

### mmap 映射大文件可能带来的内存抖动问题

`mmap` 映射大文件时，最常见的问题不是“拷贝多”，而是**页错误、页缓存争用、回收抖动**导致的性能波动。[[cloud.tencent](https://cloud.tencent.com/developer/article/2309784)]

### 为什么会抖动

- `mmap` 是按页按需加载的，访问到未驻留页面时会触发缺页中断，若访问模式不连续或跨度很大，就会出现频繁 page fault。[[blog.csdn](https://blog.csdn.net/sinat_37817094/article/details/149582368)]
- 大文件会占用大量活动页缓存，内存压力上来后，内核可能回收其他缓存页，甚至把映射页换出，之后再访问又要重新加载，形成“反复装入/驱逐”的抖动。[[cloud.tencent](https://cloud.tencent.com/developer/article/2309784)]
- 多个大文件同时 `mmap` 时，这种页缓存竞争会更明显，磁盘 I/O 队列、TLB 压力和回收行为都会放大延迟波动。[[cloud.tencent](https://cloud.tencent.com/developer/article/2309784)]

### 典型表现

- 吞吐看起来还行，但延迟尾部很差，出现明显的卡顿或响应尖刺。[[blog.csdn](https://blog.csdn.net/sinat_37817094/article/details/149582368)]
- 顺序读可能还比较稳定，但随机读、小块读取、跨页跳跃访问时抖动更严重。[[stackoverflow](https://stackoverflow.com/questions/27233564/do-memory-mapped-files-provide-advantage-for-large-buffers)]
- 在内存紧张的容器或虚拟化环境里，页面回收更激进，问题往往更容易被放大。[[gao-xiao-long.github](https://gao-xiao-long.github.io/2017/04/27/mmap-page-out/)]

### 常见缓解手段

- 尽量让访问模式局部化，批量读连续区域，避免逐元素、随机跳读。[[stackoverflow](https://stackoverflow.com/questions/27233564/do-memory-mapped-files-provide-advantage-for-large-buffers)]
- 对顺序访问场景使用 `madvise(MADV_SEQUENTIAL)` 或预读策略，减少冷页命中带来的抖动。[[blog.csdn](https://blog.csdn.net/doujinlei/article/details/145291009)]
- 对关键页可考虑 `mlock()` / `MAP_LOCKED`，避免被换出，但要注意内存锁定额度限制。[[gao-xiao-long.github](https://gao-xiao-long.github.io/2017/04/27/mmap-page-out/)]
- 如果只是纯顺序传输而不需要用户态处理，直接用 `sendfile` 往往比 `mmap` 更稳。[[developer.aliyun](https://developer.aliyun.com/article/1624567)]
- 在多文件并发或大规模数据集场景，限制并发映射数量、分块映射、必要时退回 `read()+用户态缓存`，通常更可控。[[cnblogs](https://www.cnblogs.com/friedCoder/articles/12359892.html)]

可以把它理解为：`mmap` 适合“**访问模式可预测、局部性好**”的大文件；一旦变成“**大范围随机访问、并发多、内存紧**”，就容易出现内存抖动和尾延迟恶化。[[cloud.tencent](https://cloud.tencent.com/developer/article/2309784)]

### **ioctl和unlock_ioctl有什么区别？**

- 传统`ioctl`接口在调用时需要获取大内核锁（Big Kernel Lock, BKL），这会导致性能瓶颈。
- `unlocked_ioctl`接口不依赖大内核锁，而是允许驱动程序自行处理同步机制，这样可以提高并发性能。

### **IIC原理，总线框架，设备编写方法，i2c_msg**

写寄存器的标准流程为：

1. Master发起START
2. Master发送I2C addr（7bit）和w操作0（1bit），等待ACK
3. Slave发送ACK
4. Master发送reg addr（8bit），等待ACK
5. Slave发送ACK
6. Master发送data（8bit），即要写入寄存器中的数据，等待ACK
7. Slave发送ACK
8. 第6步和第7步可以重复多次，即顺序写多个寄存器
9. Master发起STOP

在 Linux 下编写 I2C 设备的驱动通常涉及 **I2C 适配器（Adapter）、I2C 控制器（Controller）、I2C 客户端（Client）** 三个部分。一般来说，设备驱动主要针对 **I2C 客户端设备**，即 I2C 设备（如 EEPROM、传感器等）。以下是编写 Linux I2C 驱动的基本步骤：

---

### **1. I2C 设备驱动框架**

Linux 内核为 I2C 设备提供了一个标准的框架，主要涉及以下核心结构：

- **`struct i2c_driver`** —— 代表 I2C 设备驱动
- **`struct i2c_client`** —— 代表 I2C 设备（从设备）
- **`struct i2c_adapter`** —— 代表 I2C 控制器（主设备）
- **`struct i2c_algorithm`** —— 定义 I2C 硬件的访问方式

在驱动中，我们主要关心 **`i2c_client`** 和 **`i2c_driver`**，并通过 **`i2c_master_send()` 和 `i2c_master_recv()`** 进行 I2C 通信。

---

### **2. I2C 设备驱动编写步骤**

#### **(1) 设备树描述（如果是设备树驱动）**

如果你的 I2C 设备通过 **设备树（Device Tree）** 进行管理，需要在 `dts` 文件中描述设备。例如，一个 I2C 传感器的设备节点可能如下：

```
&i2c1 {
    clock-frequency = <400000>;   /* I2C 时钟频率 400kHz */
    my_sensor@50 {               /* 设备地址 0x50 */
        compatible = "mycompany,my-sensor";
        reg = <0x50>;
    };
};
```

其中：

- `compatible` 是设备匹配字符串，驱动会根据这个字符串匹配设备。
- `reg` 指定 I2C 设备的 7 位地址（0x50）。

---

#### **(2) 定义 I2C 设备信息**

在驱动代码中，定义 `i2c_device_id`（适用于非设备树驱动）和 `of_match_table`（适用于设备树驱动）：

```c
static const struct i2c_device_id my_sensor_id[] = {
    { "my-sensor", 0 },
    { }
};
MODULE_DEVICE_TABLE(i2c, my_sensor_id);

#ifdef CONFIG_OF
static const struct of_device_id my_sensor_of_match[] = {
    { .compatible = "mycompany,my-sensor" },
    { }
};
MODULE_DEVICE_TABLE(of, my_sensor_of_match);
#endif

```

---

#### **(3) I2C 读写函数**

I2C 设备的通信通常是 **发送命令 + 读取数据**，可以使用 `i2c_master_send()` 和 `i2c_master_recv()`：

```c
static int my_sensor_read(struct i2c_client *client, u8 reg, u8 *data)
{
    int ret;

    /* 先写寄存器地址 */
    ret = i2c_master_send(client, &reg, 1);
    if (ret < 0) {
        dev_err(&client->dev, "Failed to write register\n");
        return ret;
    }

    /* 读取数据 */
    ret = i2c_master_recv(client, data, 1);
    if (ret < 0) {
        dev_err(&client->dev, "Failed to read data\n");
        return ret;
    }

    return 0;
}

```

对于更复杂的 I2C 读写操作，可以使用 `i2c_transfer()`：

```c
static int my_sensor_read(struct i2c_client *client, u8 reg, u8 *data)
{
    struct i2c_msg msgs[2];

    /* 写入寄存器地址 */
    msgs[0].addr  = client->addr;
    msgs[0].flags = 0;
    msgs[0].len   = 1;
    msgs[0].buf   = &reg;

    /* 读取寄存器数据 */
    msgs[1].addr  = client->addr;
    msgs[1].flags = I2C_M_RD;
    msgs[1].len   = 1;
    msgs[1].buf   = data;

    return i2c_transfer(client->adapter, msgs, 2);
}

```

---

#### **(4) 设备初始化与注册**

在 `probe()` 函数中完成设备初始化，获取设备资源：

```c
static int my_sensor_probe(struct i2c_client *client, const struct i2c_device_id *id)
{
    u8 chip_id;
    int ret;

    dev_info(&client->dev, "Probing my_sensor on I2C bus\n");

    /* 读取传感器的 ID */
    ret = my_sensor_read(client, 0x00, &chip_id);
    if (ret < 0) {
        dev_err(&client->dev, "Failed to read chip ID\n");
        return ret;
    }

    dev_info(&client->dev, "Chip ID: 0x%02x\n", chip_id);

    return 0;
}

```

---

#### **(5) 设备注销**

在 `remove()` 函数中清理资源：

```c
static int my_sensor_remove(struct i2c_client *client)
{
    dev_info(&client->dev, "Removing my_sensor driver\n");
    return 0;
}

```

---

#### **(6) I2C 设备驱动结构**

将 `probe()` 和 `remove()` 函数绑定到 `i2c_driver`：

```c
static struct i2c_driver my_sensor_driver = {
    .driver = {
        .name  = "my-sensor",
        .of_match_table = of_match_ptr(my_sensor_of_match),
    },
    .probe    = my_sensor_probe,
    .remove   = my_sensor_remove,
    .id_table = my_sensor_id,
};

```

### **硬中断与软中断**

#### **1. 问：**对于软中断，I/O操作是否是由内核中的I/O设备驱动程序完成？

答：对于I/O请求，内核会将这项工作分派给合适的内核驱动程序，这个程序会对I/O进行队列化，以可以稍后处理（通常是磁盘I/O），或如果可能可以立即执行它。通常，当对硬中断进行回应的时候，这个队列会被驱动所处理。当一个I/O请求完成的时候，下一个在队列中的I/O请求就会发送到这个设备上。

#### 2. 问：软中断所经过的操作流程是比硬中断的少吗？换句话说，对于软中断就是：进程 ->内核中的设备驱动程序；对于硬中断：硬件->CPU->内核中的设备驱动程序？

答：是的，软中断比硬中断少了一个硬件发送信号的步骤。产生软中断的进程一定是当前正在运行的进程，因此它们不会中断CPU。但是它们会中断调用代码的流程。

### Linux 调度程序是根据进程的动态优先级还是静态优先级来调度进程的?

Liunx 调度程序是根据根据进程的动态优先级来调度进程的,但是动态优先级又是根据静态 优先级根据算法计算出来的,两者是两个相关联的值。因为高优先级的进程总是比低优先级的进程先被调度,为防止多个高优先级的进程占用 CPU 资源,导致其他进程不能占有 CPU, 所以引用动态优先级概念

### **页面置换算法**

当发生缺页中断时，如果当前内存中并没有空闲的页面，操作系统就必须在内存选择一个页面将其移出内存，以便为即将调入的页面让出空间。用来选择淘汰哪一页的规则叫做页面置换算法，可以把页面置换算法看成是淘汰页面的规则。

### 原子操作你怎么理解？为了实现一个互斥，自己定义一个变量作为标记来作为一个资源只有一个使用者行不行？

**原子操作**指的是在执行过程中不可被中断的操作。它要么全部执行完成，要么不执行，其他线程或进程在此过程中不能观察到部分执行的状态。原子操作通常用于多线程或多进程编程中，以确保对共享资源的并发访问是安全的。

#### 原子操作的关键点：

1. **不可分割性**：一旦操作开始执行，就不能被打断或分割成更小的部分。
2. **多线程安全性**：原子操作保证在多线程环境中，操作的执行不会出现数据竞争或不一致的问题。

使用自定义变量作为标记来控制资源的唯一使用者**可能行得通**，但取决于具体的实现方式和环境。简单的一个变量无法保证是**原子**的，这意味着在多线程或多进程环境中，可能会出现**竞态条件**（Race Condition），导致多个线程同时修改标记变量。

为了实现正确的互斥，必须使用**原子操作**或**硬件支持的同步机制**。例如，常见的机制有：

1. **互斥锁（Mutex）**：用操作系统提供的锁机制确保只有一个线程能够访问资源。
2. **自旋锁（Spinlock）**：如果资源被占用，线程会自旋等待，直到资源可用。
3. **硬件原语**：比如 CPU 提供的 `test_and_set`、`compare_and_swap` 等指令，它们可以保证某些操作是原子的。

在实现互斥时，必须保证对标记变量的**读写操作是原子的**，而单靠简单的标记变量不一定能保证这一点。

### 信号量和互斥量在linux中有什么区别

| **特性** | **互斥量（Mutex）** | **信号量（Semaphore）** |
| --- | --- | --- |
| **本质** | 用于**独占**访问资源，只有一个线程可以访问资源。 | 用于**计数**，控制对共享资源的多个访问权限。 |
| **值** | 二进制（0或1），要么锁住要么释放。 | 整数值，表示资源的数量。 |
| **用途** | 控制**单个线程**访问共享资源。 | 控制**多个线程/进程**访问有限的资源。 |
| **所有权** | 互斥量由加锁的线程独占，只有加锁线程可以解锁。 | 任何线程都可以改变信号量的值（无特定所有权）。 |
| **使用场景** | 用于保护临界区，防止多个线程同时访问。 | 控制并发数，如限制同时访问的线程数。 |
| **并发性** | 只能有一个线程持有锁，其他线程需等待。 | 可以有多个线程或进程并发访问资源。 |
| **线程/进程** | 主要用于线程间同步。 | 可以用于线程间或进程间同步。 |

#### 4. **总结**：

- **互斥量**适合用于确保同一时间只有一个线程访问共享资源，确保线程之间不会出现竞态条件。
- **信号量**适合用于管理多个线程或进程对有限数量资源的并发访问，能够控制并发线程或进程的数量。

---

#### 1. **互斥量（Mutex）和优先级反转**

- **优先级反转（Priority Inversion）**：
    - 互斥量可能引发**优先级反转**问题：当一个高优先级线程等待一个被低优先级线程持有的锁时，而此时中优先级的线程抢占了低优先级线程的CPU执行权，导致高优先级线程长期等待。这种情况下高优先级线程被“反转”成了低优先级。
    - **解决方案：优先级继承（Priority Inheritance）**：
        - 在使用互斥量时，Linux 中常采用**优先级继承机制**来解决优先级反转问题。当高优先级线程等待低优先级线程持有的锁时，低优先级线程临时继承高优先级的调度优先级，以防止中间优先级的线程干扰，使低优先级线程尽快完成任务释放锁。
        - **pthread_mutexattr_setprotocol()** 可以设置互斥量的优先级继承策略：
            
            ```c
            pthread_mutexattr_t attr;
            pthread_mutexattr_init(&attr);
            pthread_mutexattr_setprotocol(&attr, PTHREAD_PRIO_INHERIT);
            pthread_mutex_init(&mutex, &attr);
            ```
            
        - 当`PTHREAD_PRIO_INHERIT`被设置后，锁住互斥量的线程会临时获得高优先级线程的优先级，从而减少高优先级线程的等待时间。
- **互斥量和优先级相关特性**：
    - 在同一时刻，只允许一个线程持有锁，其他线程必须等待。
    - 高优先级线程如果竞争锁，会通过优先级继承机制减少等待时间，避免长时间被低优先级线程阻塞。

#### 2. **信号量（Semaphore）和优先级反转**

- **信号量没有直接解决优先级反转的机制**：
    - 信号量不同于互斥量，它控制的是资源的数量，而不是线程的独占访问。因此，信号量不会像互斥量那样直接导致优先级反转的典型场景。信号量没有优先级继承机制。
    - 例如，当一个低优先级线程持有信号量资源，而高优先级线程也在等待该资源时，信号量不会像互斥量那样提升低优先级线程的优先级，可能导致高优先级线程继续等待，直至资源被释放。
- **信号量与优先级的表现**：
    - 如果有多个线程等待信号量，调度器会基于线程的调度优先级决定谁可以优先获取资源（信号量）。
    - 但是，如果一个低优先级线程已经获得了信号量，高优先级线程无法像互斥量那样通过优先级继承机制来提升持有资源的低优先级线程的优先级。
    - 高优先级线程必须等低优先级线程释放信号量资源，因此优先级反转的风险依然存在，但信号量并没有专门的机制来缓解这个问题。

#### 3. **调度优先级的影响**

- **互斥量和信号量的共同点**：在高优先级线程等待资源时，调度器会优先运行高优先级的线程。如果资源被低优先级线程持有，互斥量可以通过优先级继承机制临时提升低优先级线程的调度优先级，而信号量则不会改变线程的优先级。
- **调度器策略**：Linux调度器会根据线程的优先级（实时或非实时优先级）进行调度，因此高优先级的线程通常有更高的机会获取资源或执行。

#### 4. **适用场景总结**：

- **互斥量**：
    - 更适用于需要保护临界区，且需要避免优先级反转的场景。
    - 通过优先级继承机制可以有效解决优先级反转问题，因此适合用于对实时性要求较高的系统中。
- **信号量**：
    - 更适合控制对有限资源的并发访问，但没有优先级继承机制，优先级反转问题可能会出现。
    - 适合用于不需要频繁切换资源锁定或资源竞争相对较少的场景，或多个同类资源的管理。

#### 5. **示例场景**：

- **互斥量示例**：
    
    ```c
    // 高优先级线程等待低优先级线程释放互斥量
    pthread_mutex_t mutex;
    pthread_mutex_init(&mutex, NULL);
    
    void *low_priority_task(void *arg) {
        pthread_mutex_lock(&mutex);
        // 执行较长时间的操作
        pthread_mutex_unlock(&mutex);
        return NULL;
    }
    
    void *high_priority_task(void *arg) {
        pthread_mutex_lock(&mutex);
        // 高优先级操作
        pthread_mutex_unlock(&mutex);
        return NULL;
    }
    ```
    
- **信号量示例**：
    
    ```c
    // 使用信号量控制对资源的并发访问
    sem_t semaphore;
    sem_init(&semaphore, 0, 3); // 初始值为3，表示可用资源数为3
    
    void *task(void *arg) {
        sem_wait(&semaphore);   // 等待资源
        // 执行任务，占用一个资源
        sem_post(&semaphore);   // 释放资源
        return NULL;
    }
    
    ```
    

#### 6. **总结**：

- 互斥量通过优先级继承机制有效缓解了优先级反转问题，因此适合用于需要避免高优先级线程被低优先级线程长期阻塞的场景。
- 信号量没有类似的优先级继承机制，在涉及多线程争用资源时，可能会导致优先级反转问题出现。

### linux系统打开设备文件，进程可能处于三种基本状态，如果多次打开设备文件，驱动程序应该实现什么？

在 Linux 系统中，当进程打开设备文件时，设备驱动程序需要管理不同的状态，以支持多次打开设备文件的情况。基本上，进程在打开设备文件时可能会处于以下三种状态：

1. **进程正在运行（Running）**：进程正在执行代码，可能会执行 I/O 操作。
2. **进程阻塞（Blocked）**：进程因为某些条件未满足而被挂起，例如等待 I/O 操作完成。
3. **进程挂起（Sleeping）**：进程在等待某个事件（例如数据可用）而进入睡眠状态。

对于设备驱动程序来说，如果一个设备文件被多次打开，驱动程序需要实现以下几个功能来正确处理这些状态：

#### 1. **文件描述符管理**

- **独立的文件描述符**：每次打开设备文件时，内核会为每个打开的文件分配一个唯一的文件描述符。驱动程序需要支持管理这些描述符，以区分不同的打开实例。
- **文件描述符表**：每个进程维护一个文件描述符表，这些描述符表中的条目会在设备驱动程序的 `open` 函数中被管理。

#### 2. **设备文件打开计数**

- **计数管理**：驱动程序应该在 `open` 函数中维护一个计数器来跟踪设备文件的打开次数。每次 `open` 调用时增加计数，每次 `close` 调用时减少计数。
- **打开计数处理**：如果设备不支持多个实例或需要特定的初始化/终止操作，驱动程序需要处理这些情况。例如，设备可能只允许单一打开或者需要在每次打开时执行初始化操作。

#### 3. **设备状态管理**

- **设备状态**：驱动程序应能够处理不同的设备状态（如开启、关闭、忙碌、空闲）。例如，当设备被打开时，可能需要为每个打开的实例分配特定的资源（如缓冲区）。

#### 4. **并发访问处理**

- **并发访问**：如果设备文件被多个进程打开，驱动程序需要处理并发访问，保证数据的一致性和设备的正确操作。这可能包括使用同步机制（如互斥锁、信号量等）来防止数据冲突或竞争条件。
- **设备锁**：在访问共享资源时使用设备锁来保证进程之间的同步，防止多个进程同时对设备进行非法操作。

#### 5. **`open` 和 `release` 函数**

- **`open` 函数**：驱动程序的 `open` 函数会在每次打开设备文件时被调用，通常用来执行设备初始化或检查权限等操作。
- **`release` 函数**：当进程关闭设备文件时，驱动程序的 `release` 函数被调用，用于释放设备资源或更新设备状态。

#### 6. **设备文件访问权限**

- **权限检查**：驱动程序需要根据访问模式（只读、只写、读写）检查进程的权限。如果设备需要特定的权限或操作模式，驱动程序需要进行适当的检查。

#### 驱动模块加载是在内核启动的哪个阶段？

驱动模块的加载通常发生在 **Linux 内核启动的设备初始化阶段**。具体来说，驱动模块的加载可以分为几个主要阶段，涉及从内核启动到用户空间工具协作的过程。以下是详细的步骤和阶段划分：

#### 1. **内核启动阶段**

在内核启动时，内核首先会初始化最基本的硬件和资源管理功能（如内存、CPU、时钟等）。此时，内核还未涉及设备驱动的加载。这一阶段的主要任务是引导系统，确保能够顺利进入设备初始化阶段。

#### 2. **设备初始化阶段**

内核启动后，会进入设备初始化阶段，开始进行与硬件设备相关的探测和初始化。这一阶段会根据不同总线（如 PCI、USB 等）来识别已连接的设备，并尝试加载相应的驱动模块。这一过程通常分为以下步骤：

- **设备发现与枚举**：内核通过 PCI、USB、ACPI、I2C 等总线机制，自动发现并枚举当前系统中连接的硬件设备。
- **驱动注册机制**：每个设备都有相应的驱动程序，驱动程序通过内核中的 `module_init()` 函数注册自身。当设备被内核探测到时，内核会根据设备类型、厂商 ID、设备 ID 等信息，在内核中查找已注册的驱动程序，并尝试匹配到合适的驱动。

#### 3. **内核模块加载阶段**

- **内置驱动模块**：某些驱动模块是直接编译进内核的，这些模块在内核启动的设备初始化阶段就会被自动加载。这种模块无需额外的用户空间干预，因为它们是内核的一部分，直接在内核内执行。
- **外部加载驱动模块**：一些驱动模块并未编译到内核中，而是作为独立的模块（`.ko` 文件）进行动态加载。这些模块通常由用户空间的工具（如 `udev`）来触发加载。
    - **modprobe 和 insmod**：如果某些驱动需要外部加载，Linux 内核会通过 `modprobe` 或 `insmod` 命令动态加载这些模块。在设备初始化阶段，内核检测到硬件设备后，会通过设备 ID 找到合适的模块文件并将其加载到内核中。
    - **自动加载机制**：当内核探测到新设备时，会通过设备描述信息查找合适的驱动。如果驱动是模块化的，内核会尝试从文件系统中加载该模块，通常通过 `modprobe` 或 `udev` 动态加载。

#### 4. **用户空间工具协作（udev）**

当内核完成基本的设备初始化后，用户空间的设备管理工具（如 **udev**）会进一步协助设备的驱动加载：

- **udev** 是 Linux 系统的设备管理守护进程，它在内核启动过程中会监听来自内核的设备事件（如设备插入或移除）。
- **热插拔支持**：当 `udev` 监听到设备连接事件时，它会查找与设备匹配的驱动模块，并调用 `modprobe` 来加载适当的模块。
- **设备节点创建**：`udev` 还会为每个加载的驱动程序创建相应的设备节点（通常位于 `/dev` 目录下），以便用户空间程序能够与设备交互。

#### 5. **用户空间启动阶段**

内核启动并加载所有必要的驱动模块后，会切换到用户空间，启动系统的主进程（通常是 `init` 系统）。在这个阶段，用户空间工具（如 `systemd`、`udev`）可能继续加载某些用户空间驱动或执行设备配置。

#### 总结

- **设备驱动模块的加载** 主要发生在内核的 **设备初始化阶段**。内核首先通过各种总线（如 PCI、USB 等）识别已连接的设备，并尝试加载内置驱动或模块化驱动。
- 如果驱动是以 **模块化方式** 存在的，内核会通过 `modprobe` 或 `udev` 等工具自动加载合适的驱动模块。
- 对于一些需要 **动态加载** 的设备（如热插拔设备），在系统启动完成后，`udev` 等用户空间工具负责继续监控并加载相应的驱动。

通过这一系列的步骤，Linux 内核能够动态探测和加载各种硬件设备的驱动模块，确保系统能够正常运行并与硬件设备交互。

#### 上电到第一行c代码

整个 Linux 0.11 从计算机上电启动，到成功执行第一行 C 语言代码（`init/main.c` 中的 `main()` 函数），是一段将硬件与软件精妙结合的“苦力活”。整个过程由汇编语言编写的三个核心程序主导：`bootsect.s`、`setup.s` 和 `head.s`。以下是这段宏大旅程的详细拆解：

#### 第一阶段：BIOS 加载与代码搬家 (`bootsect.s`)

1. **BIOS 上电自检**：当 PC 电源打开后，CPU 自动进入 16 位实模式，并从 ROM-BIOS 中的地址 `0xFFFF0` 开始自动执行代码。BIOS 会执行系统检测，并在物理地址 0 处初始化中断向量表。
2. **加载引导扇区**：BIOS 会将启动设备（如硬盘或软盘）的第一个扇区（引导扇区，共 512 字节的 `bootsect.s` 编译产生的机器码）读取到内存的绝对地址 `0x7C00` 处，并跳转到此处开始执行。
3. **自我搬移**：因为 `0x7C00` 空间狭小，`bootsect.s` 做的第一件事就是把自己原封不动地复制到内存 `0x90000` 处，并通过 `jmpi go, 0x9000` 指令跳转到新位置继续执行。
4. **规划初始内存与加载系统**：在 `0x90000` 处，`bootsect.s` 设置了数据段、代码段以及栈顶指针（指向 `0x9FF00` 处，远离代码区以防冲突）。随后，它利用 BIOS 中断（`int 0x13`）将紧随其后的 4 个扇区的 `setup.s` 代码加载到内存 `0x90200` 处。接着，将操作系统的核心模块（`system` 模块，包含 `head.s` 和所有 C 代码）从磁盘加载到内存的 `0x10000` 处。
5. **交接控制权**：全部加载完毕后，通过一个段间跳转指令 `jmpi 0, 0x9020`，CPU 跳转到 `setup.s` 的开头继续执行。

#### 第二阶段：获取硬件参数与切换保护模式 (`setup.s`)

1. **获取硬件信息**：`setup.s` 此时仍运行在实模式下。它频繁调用 BIOS 提供的中断例程，获取机器的各项硬件参数（如光标位置、扩展内存大小、显卡模式、硬盘参数等），并将这些参数统统覆盖保存在内存 `0x90000` 开始的位置，供后续的 C 程序使用。
2. **移动 System 模块**：为了让内核代码的地址等于实际的物理地址，`setup.s` 关掉中断（`cli`），将存放在 `0x10000` 处的庞大 `system` 模块整体向下移动，直接覆盖掉内存最开始的 `0x00000` 处。
3. **设置临时描述符表与开启 A20**：为进入 32 位保护模式做准备，`setup.s` 使用 `lidt` 和 `lgdt` 指令加载了临时的中断描述符表（IDT）和全局描述符表（GDT）。紧接着，通过向键盘控制器 `0x64` 和 `0x60` 端口发送命令，开启了 A20 地址线，突破了实模式下的 1MB 寻址瓶颈。
4. **重新编程 8259A 中断控制器**：由于 IBM PC 原本的中断设计（`0x08-0x0F`）与 Intel 保护模式下的异常中断号冲突，`setup.s` 对中断控制器进行了重新编程，将硬件中断号移到了 `0x20-0x2F`。
5. **纵身一跃进入保护模式**：将 CPU 机器状态字控制寄存器 `CR0` 的第 0 位（PE 位）置为 1，正式开启 32 位保护模式。最后通过指令 `jmpi 0, 8`，跳转到内存 `0x00000` 处开始执行（此处的 8 是保护模式下的段选择子，指向 GDT 中的代码段，偏移为 0）。

#### 第三阶段：建立分页机制与跳转 C 语言 (`head.s`)

处于 `0x00000` 处的代码正是 `system` 模块的头部 `head.s`，此时系统已完全运行在 32 位保护模式下，且使用的是 AT&T 汇编语法。

1. **重载段寄存器与内核堆栈**：重新把数据段寄存器（ds, es, fs, gs）配置为指向数据段，并利用 `lss _stack_start, %esp` 指令设置真正的系统内核堆栈。
2. **重建真正的 IDT 和 GDT**：废弃 `setup.s` 中的临时表，在内存中重新构建含有 256 个表项的 IDT（默认全部指向一个只报未知的哑中断函数 `ignore_int`）以及新的 GDT。
3. **检测硬件**：使用物理地址 `0` 与 `1M` 处的内容比较来检验 A20 地址线是否真正开启，并检测系统是否包含数学协处理器。
4. **巧妙压栈准备跳转**：在开启分页机制之前，`head.s` 施展了一个极其巧妙的压栈操作：它依次将环境变量指针（`0`）、命令行参数指针（`0`）、参数个数（`0`）、返回地址（`L6` 的地址）压入堆栈，**最后将 C 语言主函数 `_main` 的入口地址压入堆栈**。
5. **开启分页机制并跳入 C 代码**：紧接着，程序跳转去执行 `setup_paging`。该子程序在内存物理地址 `0x0000` 处（直接覆盖掉了 `head.s` 自己开头的代码）建立页目录表和 4 个页表（可寻址 16MB 内存），然后将页目录基址写入 `CR3` 寄存器，并把 `CR0` 的最高位（PG 位）置 1，彻底开启了内存分页机制。
6. **最终汇合 (`ret`)**：`setup_paging` 子程序的最后一条指令是 `ret`（返回指令）。此时 CPU 会机械地从栈顶弹出一个地址赋给指令指针寄存器 EIP。而在此前我们刚刚把 `_main` 函数的地址压在了栈顶！因此，**这个 `ret` 指令没有返回到任何调用它的地方，而是直接导致 CPU 跳转到了 `init/main.c` 中的 `void main(void)` 处**。

至此，硬件初始化和底层架构的苦力活全部结束，系统控制权正式交接给了 C 语言，Linux 的内核主干初始化工作（`mem_init`、`trap_init`、`sched_init` 等）由此拉开帷幕。

#### 进入保护模式后，原本的 IDT 中断描述符表有什么作用？

进入保护模式后，原本的中断表（包括实模式下的 BIOS 中断向量表，以及进入保护模式前临时加载的 IDT）**实际上没有任何作用，它们会被内核彻底废弃并被新数据覆盖**。

为了让你清晰地了解这一过程，我们可以把 Linux 0.11 启动阶段中断表的演变分为四个阶段：

**1. 实模式下的 BIOS 中断向量表（用完即被覆盖）：**
在系统刚开机处于实模式下时，物理内存 `0x0000` 处存放着 BIOS 初始化的中断向量表（大小为 1KB）。在进入保护模式之前，操作系统（`setup.s` 代码）必须利用这个表调用 BIOS 中断来获取机器的核心硬件参数（如显卡模式、硬盘参数等）。一旦获取完毕并准备进入保护模式，内核就会把 `system` 模块整体移动到内存 `0x0000` 开始的位置，这意味着**原本的 BIOS 中断向量表完成了历史使命，被无情地直接覆盖掉了**。

**2. 切换保护模式前的“临时 IDT”（纯粹为了满足 CPU 硬件机制）：**
在 `setup.s` 程序末尾，为了让 CPU 能够合法地切换到 32 位保护模式，系统必须通过 `lidt` 指令加载一个中断描述符表（IDT）。但是，这里加载的“临时 IDT”的表长度被设置为 0，基址也是 0。由于此时系统已经使用 `cli` 指令彻底屏蔽了所有硬件中断，这个临时的 IDT **纯粹是为了应付 Intel CPU 切换保护模式时的硬件规范约束**，实际上没有任何处理中断的能力。

**3. 进入保护模式后的“初始 IDT”（充当过渡的安全网）：**
进入保护模式并跳转到 `head.s` 模块执行后，原本过渡用的临时 IDT 被废弃。内核会在内存中重新构建一个真正的、包含 256 个表项的新 IDT。不过为了安全起见，此时**所有的表项都会默认指向同一个名为 `ignore_int` 的哑中断处理程序**（一旦触发，仅仅会在屏幕上打印一条 "Unknown interrupt" 错误信息）。这个初始 IDT 的核心作用是充当安全网，防止在操作系统真正建好各项硬件驱动之前，发生意外的硬件中断导致系统崩溃。

**4. 最终发挥作用的 IDT（在系统初始化中逐步完善）：**
随着代码继续执行到 C 语言编写的 `init/main.c`，系统会通过调用 `trap_init()`、`sched_init()`、`hd_init()` 等初始化函数，逐步将真正有用的硬件异常处理程序、系统调用门（int 0x80）、时钟中断和硬盘中断等的真实入口地址，覆盖到这个 IDT 对应的表项中去，这才形成了操作系统运行时真正依赖的 IDT。

**总结来说**：进入保护模式后，原本的中断描述符表完全失去了作用。保护模式下真正起作用的 IDT，是操作系统在进入保护模式后（`head.s` 阶段）从零开始重新构建，并在 `main.c` 的初始化函数中逐步替换完善的。

#### 分页建立

在 Linux 0.11 的 `head.s` 程序中，建立分页机制的核心代码位于 `setup_paging` 子程序。由于当时的 Linux 0.11 默认支持的最大物理内存为 16MB，因此内核只需建立 1 个页目录表和 4 个页表就能完成对这 16MB 内存空间的恒等映射（即线性地址等于物理地址）。

具体建立分页的过程可以拆解为以下六个步骤：

**第一步：为页目录和页表开辟并清空内存**
程序首先将从物理地址 `0x0000` 开始的 5 页物理内存（共 20KB）全部清零。这 5 页内存中，第 1 页将用作**页目录表**，后续 4 页用作 4 个**页表**。这里恰好覆盖了 `head.s` 最开头自身的代码，因为这些代码已经执行过了，所以可以直接被覆盖挪作他用。

**第二步：设置页目录项（PDE）**
在清空内存后，程序设置了页目录表（位于 `0x0000`）的前 4 个有效目录项。这 4 个目录项分别指向紧随其后的 4 个页表（它们分别位于物理地址 `0x1000`、`0x2000`、`0x3000`、`0x4000` 处）。同时，这 4 个目录项的属性标志都被设置为 `7`（二进制 `0b111`），代表这些页表是存在的（Present）、并且允许用户级别读写（User R/W）。

**第三步：填写页表项（PTE）建立具体映射**
接下来，程序开始为这 4 个页表填写具体的页表项。4 个页表每个包含 1024 项，共有 4096 个页表项，每个页表项映射 4KB 内存，恰好能够完整映射 16MB 的物理内存空间。
为了高效，这段代码采用了**从高地址向低地址倒退填写**的方式。它从最后一个页表的最后一个表项（即偏移 `pg3+4092` 处）开始，将其指向物理内存的最末端 `0xFFF000` 处，加上属性标志 `7`，即填入的内容为 `0xFFF007`。然后地址每次减去一页的大小（`0x1000`，即 4KB），循环填写，直到第一页表的第一个表项被填充满。至此，0~16MB 的线性地址空间就被一一对应到了物理地址上。

**第四步：设置 CR3 寄存器告知 CPU 页目录位置**
页目录和页表在内存中建立好之后，需要将页目录的起始位置告诉 CPU。程序通过将物理基地址 `0x0000` 写入 `CR3` 寄存器（也被称为页目录基址寄存器 PDBR），完成了与硬件内存管理单元（MMU）的交接。

**第五步：开启分页开关（修改 CR0 寄存器）**
一切准备就绪后，程序读取控制寄存器 `CR0`，将其最高位（第 31 位，即 PG 分页标志位）强行置为 1（通过与 `0x80000000` 进行或运算），然后再写回 `CR0`。这标志着 32 位分页内存管理机制正式激活。

**第六步：刷新指令队列并跳转到 C 语言核心**
开启分页后，`setup_paging` 子程序执行的最后一条指令是 `ret`（返回指令）。这条指令具有双重极其巧妙的作用：

1. 它强制 CPU 刷新指令预取队列，以保证后续指令能正确使用刚刚开启的分页机制进行地址转换。
2. 在调用分页子程序之前，程序曾人为地往堆栈中压入了 C 语言主函数 `_main` 的入口地址。`ret` 指令此时会机械地将栈顶的 `_main` 函数地址弹出到指令指针寄存器 EIP 中，从而实现“假返回、真跳转”，让系统控制流平滑地过渡到 `init/main.c` 里的 `main()` 函数，正式进入 C 语言的世界。
