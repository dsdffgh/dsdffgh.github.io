整个 Linux 0.11 从计算机上电启动，到成功执行第一行 C 语言代码（`init/main.c` 中的 `main()` 函数），是一段将硬件与软件精妙结合的“苦力活”。整个过程由汇编语言编写的三个核心程序主导：`bootsect.s`、`setup.s` 和 `head.s`。以下是这段宏大旅程的详细拆解：

## 第一阶段：BIOS 加载与代码搬家 (`bootsect.s`)

1. **BIOS 上电自检**：当 PC 电源打开后，CPU 自动进入 16 位实模式，并从 ROM-BIOS 中的地址 `0xFFFF0` 开始自动执行代码。BIOS 会执行系统检测，并在物理地址 0 处初始化中断向量表。
2. **加载引导扇区**：BIOS 会将启动设备（如硬盘或软盘）的第一个扇区（引导扇区，共 512 字节的 `bootsect.s` 编译产生的机器码）读取到内存的绝对地址 `0x7C00` 处，并跳转到此处开始执行。
3. **自我搬移**：因为 `0x7C00` 空间狭小，`bootsect.s` 做的第一件事就是把自己原封不动地复制到内存 `0x90000` 处，并通过 `jmpi go, 0x9000` 指令跳转到新位置继续执行。
4. **规划初始内存与加载系统**：在 `0x90000` 处，`bootsect.s` 设置了数据段、代码段以及栈顶指针（指向 `0x9FF00` 处，远离代码区以防冲突）。随后，它利用 BIOS 中断（`int 0x13`）将紧随其后的 4 个扇区的 `setup.s` 代码加载到内存 `0x90200` 处。接着，将操作系统的核心模块（`system` 模块，包含 `head.s` 和所有 C 代码）从磁盘加载到内存的 `0x10000` 处。
5. **交接控制权**：全部加载完毕后，通过一个段间跳转指令 `jmpi 0, 0x9020`，CPU 跳转到 `setup.s` 的开头继续执行。

## 第二阶段：获取硬件参数与切换保护模式 (`setup.s`)

1. **获取硬件信息**：`setup.s` 此时仍运行在实模式下。它频繁调用 BIOS 提供的中断例程，获取机器的各项硬件参数（如光标位置、扩展内存大小、显卡模式、硬盘参数等），并将这些参数统统覆盖保存在内存 `0x90000` 开始的位置，供后续的 C 程序使用。
2. **移动 System 模块**：为了让内核代码的地址等于实际的物理地址，`setup.s` 关掉中断（`cli`），将存放在 `0x10000` 处的庞大 `system` 模块整体向下移动，直接覆盖掉内存最开始的 `0x00000` 处。
3. **设置临时描述符表与开启 A20**：为进入 32 位保护模式做准备，`setup.s` 使用 `lidt` 和 `lgdt` 指令加载了临时的中断描述符表（IDT）和全局描述符表（GDT）。紧接着，通过向键盘控制器 `0x64` 和 `0x60` 端口发送命令，开启了 A20 地址线，突破了实模式下的 1MB 寻址瓶颈。
4. **重新编程 8259A 中断控制器**：由于 IBM PC 原本的中断设计（`0x08-0x0F`）与 Intel 保护模式下的异常中断号冲突，`setup.s` 对中断控制器进行了重新编程，将硬件中断号移到了 `0x20-0x2F`。
5. **纵身一跃进入保护模式**：将 CPU 机器状态字控制寄存器 `CR0` 的第 0 位（PE 位）置为 1，正式开启 32 位保护模式。最后通过指令 `jmpi 0, 8`，跳转到内存 `0x00000` 处开始执行（此处的 8 是保护模式下的段选择子，指向 GDT 中的代码段，偏移为 0）。

## 第三阶段：建立分页机制与跳转 C 语言 (`head.s`)

处于 `0x00000` 处的代码正是 `system` 模块的头部 `head.s`，此时系统已完全运行在 32 位保护模式下，且使用的是 AT&T 汇编语法。

1. **重载段寄存器与内核堆栈**：重新把数据段寄存器（ds, es, fs, gs）配置为指向数据段，并利用 `lss _stack_start, %esp` 指令设置真正的系统内核堆栈。
2. **重建真正的 IDT 和 GDT**：废弃 `setup.s` 中的临时表，在内存中重新构建含有 256 个表项的 IDT（默认全部指向一个只报未知的哑中断函数 `ignore_int`）以及新的 GDT。
3. **检测硬件**：使用物理地址 `0` 与 `1M` 处的内容比较来检验 A20 地址线是否真正开启，并检测系统是否包含数学协处理器。
4. **巧妙压栈准备跳转**：在开启分页机制之前，`head.s` 施展了一个极其巧妙的压栈操作：它依次将环境变量指针（`0`）、命令行参数指针（`0`）、参数个数（`0`）、返回地址（`L6` 的地址）压入堆栈，**最后将 C 语言主函数 `_main` 的入口地址压入堆栈**。
5. **开启分页机制并跳入 C 代码**：紧接着，程序跳转去执行 `setup_paging`。该子程序在内存物理地址 `0x0000` 处（直接覆盖掉了 `head.s` 自己开头的代码）建立页目录表和 4 个页表（可寻址 16MB 内存），然后将页目录基址写入 `CR3` 寄存器，并把 `CR0` 的最高位（PG 位）置 1，彻底开启了内存分页机制。
6. **最终汇合 (`ret`)**：`setup_paging` 子程序的最后一条指令是 `ret`（返回指令）。此时 CPU 会机械地从栈顶弹出一个地址赋给指令指针寄存器 EIP。而在此前我们刚刚把 `_main` 函数的地址压在了栈顶！因此，**这个 `ret` 指令没有返回到任何调用它的地方，而是直接导致 CPU 跳转到了 `init/main.c` 中的 `void main(void)` 处**。

至此，硬件初始化和底层架构的苦力活全部结束，系统控制权正式交接给了 C 语言，Linux 的内核主干初始化工作（`mem_init`、`trap_init`、`sched_init` 等）由此拉开帷幕。

## 进入保护模式后，原本的 IDT 中断描述符表有什么作用？

进入保护模式后，原本的中断表（包括实模式下的 BIOS 中断向量表，以及进入保护模式前临时加载的 IDT）**实际上没有任何作用，它们会被内核彻底废弃并被新数据覆盖**。

为了让你清晰地了解这一过程，我们可以把 Linux 0.11 启动阶段中断表的演变分为四个阶段：

**1. 实模式下的 BIOS 中断向量表（用完即被覆盖）：**
 在系统刚开机处于实模式下时，物理内存 `0x0000` 处存放着 BIOS 初始化的中断向量表（大小为 1KB）。在进入保护模式之前，操作系统（`setup.s` 代码）必须利用这个表调用 BIOS 中断来获取机器的核心硬件参数（如显卡模式、硬盘参数等）。一旦获取完毕并准备进入保护模式，内核就会把 `system` 模块整体移动到内存 `0x0000` 开始的位置，这意味着**原本的 BIOS 中断向量表完成了历史使命，被无情地直接覆盖掉了**。

**2. 切换保护模式前的“临时 IDT”（纯粹为了满足 CPU 硬件机制）：**
 在 `setup.s` 程序末尾，为了让 CPU 能够合法地切换到 32 位保护模式，系统必须通过 `lidt` 指令加载一个中断描述符表（IDT）。但是，这里加载的“临时 IDT”的表长度被设置为 0，基址也是 0。由于此时系统已经使用 `cli` 指令彻底屏蔽了所有硬件中断，这个临时的 IDT **纯粹是为了应付 Intel CPU 切换保护模式时的硬件规范约束**，实际上没有任何处理中断的能力。

**3. 进入保护模式后的“初始 IDT”（充当过渡的安全网）：**
 进入保护模式并跳转到 `head.s` 模块执行后，原本过渡用的临时 IDT 被废弃。内核会在内存中重新构建一个真正的、包含 256 个表项的新 IDT。不过为了安全起见，此时**所有的表项都会默认指向同一个名为 `ignore_int` 的哑中断处理程序**（一旦触发，仅仅会在屏幕上打印一条 "Unknown interrupt" 错误信息）。这个初始 IDT 的核心作用是充当安全网，防止在操作系统真正建好各项硬件驱动之前，发生意外的硬件中断导致系统崩溃。

**4. 最终发挥作用的 IDT（在系统初始化中逐步完善）：**
 随着代码继续执行到 C 语言编写的 `init/main.c`，系统会通过调用 `trap_init()`、`sched_init()`、`hd_init()` 等初始化函数，逐步将真正有用的硬件异常处理程序、系统调用门（int 0x80）、时钟中断和硬盘中断等的真实入口地址，覆盖到这个 IDT 对应的表项中去，这才形成了操作系统运行时真正依赖的 IDT。

**总结来说**：进入保护模式后，原本的中断描述符表完全失去了作用。保护模式下真正起作用的 IDT，是操作系统在进入保护模式后（`head.s` 阶段）从零开始重新构建，并在 `main.c` 的初始化函数中逐步替换完善的。

## 分页建立

在 Linux 0.11 的 `head.s` 程序中，建立分页机制的核心代码位于 `setup_paging` 子程序。由于当时的 Linux 0.11 默认支持的最大物理内存为 16MB，因此内核只需建立 1 个页目录表和 4 个页表就能完成对这 16MB 内存空间的恒等映射（即线性地址等于物理地址）。

具体建立分页的过程可以拆解为以下六个步骤：

**第一步：为页目录和页表开辟并清空内存**
 程序首先将从物理地址 `0x0000` 开始的 5 页物理内存（共 20KB）全部清零。这 5 页内存中，第 1 页将用作**页目录表**，后续 4 页用作 4 个**页表**。这里恰好覆盖了 `head.s` 最开头自身的代码，因为这些代码已经执行过了，所以可以直接被覆盖挪作他用。

**第二步：设置页目录项（PDE）**
 在清空内存后，程序设置了页目录表（位于 `0x0000`）的前 4 个有效目录项。这 4 个目录项分别指向紧随其后的 4 个页表（它们分别位于物理地址 `0x1000`、`0x2000`、`0x3000`、`0x4000` 处）。同时，这 4 个目录项的属性标志都被设置为 `7`（二进制 `0b111`），代表这些页表是存在的（Present）、并且允许用户级别读写（User R/W）。

**第三步：填写页表项（PTE）建立具体映射**
 接下来，程序开始为这 4 个页表填写具体的页表项。4 个页表每个包含 1024 项，共有 4096 个页表项，每个页表项映射 4KB 内存，恰好能够完整映射 16MB 的物理内存空间。
 为了高效，这段代码采用了**从高地址向低地址倒退填写**的方式。它从最后一个页表的最后一个表项（即偏移 `pg3+4092` 处）开始，将其指向物理内存的最末端 `0xFFF000` 处，加上属性标志 `7`，即填入的内容为 `0xFFF007`。然后地址每次减去一页的大小（`0x1000`，即 4KB），循环填写，直到第一页表的第一个表项被填充满。至此，0~16MB 的线性地址空间就被一一对应到了物理地址上。

**第四步：设置 CR3 寄存器告知 CPU 页目录位置**
 页目录和页表在内存中建立好之后，需要将页目录的起始位置告诉 CPU。程序通过将物理基地址 `0x0000` 写入 `CR3` 寄存器（也被称为页目录基址寄存器 PDBR），完成了与硬件内存管理单元（MMU）的交接。

**第五步：开启分页开关（修改 CR0 寄存器）**
 一切准备就绪后，程序读取控制寄存器 `CR0`，将其最高位（第 31 位，即 PG 分页标志位）强行置为 1（通过与 `0x80000000` 进行或运算），然后再写回 `CR0`。这标志着 32 位分页内存管理机制正式激活。

**第六步：刷新指令队列并跳转到 C 语言核心**
 开启分页后，`setup_paging` 子程序执行的最后一条指令是 `ret`（返回指令）。这条指令具有双重极其巧妙的作用：

1. 它强制 CPU 刷新指令预取队列，以保证后续指令能正确使用刚刚开启的分页机制进行地址转换。
2. 在调用分页子程序之前，程序曾人为地往堆栈中压入了 C 语言主函数 `_main` 的入口地址。`ret` 指令此时会机械地将栈顶的 `_main` 函数地址弹出到指令指针寄存器 EIP 中，从而实现“假返回、真跳转”，让系统控制流平滑地过渡到 `init/main.c` 里的 `main()` 函数，正式进入 C 语言的世界。
