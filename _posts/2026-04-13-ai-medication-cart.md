这篇记录整理的是一个基于 AI 视觉识别和 STM32 实时控制的小车项目。系统目标是让小车通过摄像头识别葡萄目标，完成目标定位、路径靠近、避障和给药动作。项目整体并不是单一算法验证，而是一次从模型训练、AI 板部署、视频流处理、串口通信到下位机运动控制的完整联调。

## 系统链路

整个系统被拆成五个部分：模型训练与板端部署、视频采集与预处理、AI 推理与后处理、AI 板到 STM32 的串口通信、STM32 侧的实时运动控制。

模型侧采用 YOLOv3 做目标检测。训练阶段在 PC 或 GPU 环境中准备葡萄图片数据集，通过标注工具生成检测框，再在 Darknet 或 PyTorch 框架中训练模型。板端推理使用 NNIE，因此训练后的模型还要转换到 Caffe 格式，再通过 RuyiStudio 和 `nnie_mapper` 完成量化，生成能在板端运行的 `.wk` 文件。

视频流由摄像头进入 VI，再经过 ISP 和 VPSS。VPSS 的作用很关键，它把同一份视频流分成不同用途的通道：一路保留较高分辨率，用于显示或录像；另一路缩放到模型输入尺寸，送入 NNIE 做推理。图像缩放和格式转换由硬件通路完成，应用层主要负责配置分辨率、通道属性和数据流向。

AI 推理阶段调用 `HI_MPI_SVP_NNIE_Forward`，将 VPSS 输出的小尺寸图像送入 NNIE。YOLOv3 的输出还不能直接用于控制，需要在 CPU 上完成候选框解码、置信度过滤和 NMS。最终得到目标类别、置信度和边界框坐标后，再把模型坐标映射回实际画面坐标。

控制侧更关注目标中心点和目标框面积。目标中心点用于计算横向偏差，目标框面积作为距离的近似判断条件。AI 板把目标标志、中心坐标、面积等数据打包成串口帧，发送给 STM32。STM32 收到数据后，在 FreeRTOS 任务中更新控制目标，再通过 PID 和运动学计算输出电机 PWM 与舵机角度。

## 视觉坐标到控制量

模型输出通常基于输入尺寸，例如 416x416。控制逻辑使用的是实际画面坐标，所以需要做比例映射：

```text
实际 X = 模型 X / 模型输入宽度 * 原始画面宽度
实际 Y = 模型 Y / 模型输入高度 * 原始画面高度
```

映射后计算目标中心点：

```text
center_x = (xmin + xmax) / 2
error_x = center_x - frame_width / 2
area = (xmax - xmin) * (ymax - ymin)
```

`error_x` 表示目标相对画面中心的偏移，控制侧根据这个偏差调整前轮转角或左右轮差速。`area` 用于判断接近程度，面积超过阈值时进入给药动作。这个处理比较朴素，但在项目阶段足够直接，调参时也容易观察。

## 串口通信协议

AI 板和 STM32 之间使用 UART。最开始如果只传原始字节流，接收端无法可靠判断一帧数据从哪里开始、在哪里结束。电机运行时还会带来电磁干扰，串口线上可能出现错位、丢字节或位翻转，裸字节流很容易把异常数据当成有效坐标。

后续通信帧设计成固定结构：

```text
| 帧头 | 长度 | 功能码 | 数据 | 校验 | 帧尾 |
```

一个目标检测帧可以包含目标是否存在、中心 X/Y、面积或宽高等字段。STM32 侧解析时先找帧头，再检查长度和帧尾，最后做校验。校验失败的数据包直接丢弃，控制任务继续使用上一帧可信状态或进入短时丢失处理。

接收侧使用 DMA 加串口空闲中断。DMA 负责连续搬运字节，USART IDLE 中断用于判断一段数据接收结束。中断里只做轻量处理，协议解析放到 FreeRTOS 任务中执行。这样可以减少中断耗时，同时避免控制任务被串口解析长时间占用。

## FreeRTOS 任务划分

STM32 侧采用 FreeRTOS 管理多个周期任务。控制类任务优先级最高，显示、指示灯等任务优先级较低。

| 任务名称 | 功能 | 优先级 | 周期 |
| --- | --- | --- | --- |
| `Balance_task` | 电机速度计算和运动控制 | 最高 | 100Hz |
| `MPU6050_task` | IMU 数据读取 | 中等 | 100Hz |
| `data_task` | 串口或 CAN 数据发送 | 中等 | 20Hz |
| `show_task` | OLED 显示 | 低 | 20Hz |
| `led_task` | 指示灯状态 | 低 | 10Hz |

`Balance_task` 是控制核心。它读取编码器反馈，计算目标速度和转向角，再通过 PI/PID 控制输出 PWM。串口接收任务只负责把 AI 板数据解析成结构化目标，不直接控制电机。这样任务边界比较清楚，视觉、通信、控制之间不会互相混在一起。

## 运动控制

小车采用阿克曼转向模型。控制输入可以抽象为前进速度 `Vx` 和转向角 `AngleR`。当存在转向角时，根据轴距和轮距计算转弯半径，再得到左右轮目标速度：

```text
R = Axle_spacing / tan(AngleR) - 0.5 * Wheel_spacing
MOTOR_A.Target = Vx * (R - 0.5 * Wheel_spacing) / R
MOTOR_B.Target = Vx * (R + 0.5 * Wheel_spacing) / R
```

舵机角度不是简单线性映射。机械结构、舵机安装误差和转向连杆都会引入非线性，因此项目中使用二次曲线拟合做校正：

```c
Angle_Servo = -0.2137f * pow(AngleR, 2) + 1.439f * AngleR + 0.009599f;
```

速度环采用增量式 PI，计算量低，适合 STM32 这类实时控制场景：

```c
int Incremental_PI_A(int Encoder, int Target)
{
    static int Bias, Pwm, Last_bias;
    Bias = Encoder - Target;
    Pwm += Velocity_KP * (Bias - Last_bias) + Velocity_KI * Bias;
    if (Pwm > 7200) Pwm = 7200;
    if (Pwm < -7200) Pwm = -7200;
    Last_bias = Bias;
    return Pwm;
}
```

调参时先降低积分项影响，把比例项调到响应足够快但不过度振荡，再逐步增加积分项消除稳态误差。实际效果不只看波形，还要看车体在低速、转向、负载变化和地面不平时的动作是否连贯。

## IMU 和视觉的配合

视觉帧率通常低于底层控制频率。目标检测输出大约十几到二十帧每秒，而 `MPU6050_task` 和控制任务可以到 100Hz。仅依赖视觉纠偏时，车体容易出现滞后和摆动。

IMU 在这个项目中主要用于航向角变化的局部补偿。视觉给出目标方向后，在下一帧视觉结果到来之前，STM32 可以根据 IMU 的 Yaw 角变化做快速修正，让小车靠近目标时更平顺。这个设计没有把所有姿态问题都处理完，例如上坡时的重力补偿还没有纳入速度环，但任务结构已经给后续扩展留下了位置。

## 联调问题记录

项目中最典型的问题出现在软硬联调阶段：小车偶尔突然急转或猛冲，现象没有固定规律。最初从视觉误检、控制任务和 PID 参数三个方向排查，都没有复现出异常。拔掉电机电源后观察 AI 板输出，目标坐标稳定；在 STM32 内部模拟固定坐标输入，电机控制也正常。

最后问题落在串口通信链路。电机运行时产生的干扰让串口数据出现错位和错误字节，STM32 把异常数据解析成很大的坐标偏差，进而输出过大的 PWM。通信协议加入帧头、长度、校验和帧尾后，异常帧可以被识别并丢弃，小车乱动的问题消失。

这次问题给项目留下的经验很直接：机电系统里，通信协议不能只满足“正常情况下能传”。电机、供电、线束和接地都会影响数据可靠性，协议层需要具备发现错误和丢弃错误的能力。

## 项目复盘

这个项目真正有价值的地方，不在于单独使用 YOLOv3 或 FreeRTOS，而在于把视觉结果变成可执行的运动控制目标。AI 板负责把复杂图像变成结构化坐标，STM32 负责把坐标变成稳定动作。两者之间通过可靠的串口协议连接，系统才具备持续运行的基础。

后续可以继续优化的方向包括：使用更轻量的检测模型提高帧率；加入目标短时丢失后的状态保持策略；把 IMU 的 Pitch 信息用于坡度前馈补偿；对通信协议增加序号和超时机制；在 AI 板端记录推理耗时、串口发送时间和 STM32 响应时间，形成更完整的闭环延迟分析。
